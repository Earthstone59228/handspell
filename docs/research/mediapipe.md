# MediaPipe Hand Landmarker — verified 2026-09-13

## 1. Android artifact

- `com.google.mediapipe:tasks-vision` is **not on Maven Central** — it's on Google's Maven repo (`google()` in Gradle, backed by `dl.google.com`/`maven.google.com`). Latest stable per group metadata is **1.0.0** (mvnrepository also lists 0.10.29 as a recent point release before the 1.0.0 jump). Source: https://dl.google.com/dl/android/maven2/com/google/mediapipe/tasks-vision/maven-metadata.xml , https://mvnrepository.com/artifact/com.google.mediapipe/tasks-vision
- Official setup guide states **minSdk 24** for MediaPipe Tasks on Android (older per-task guide text says minSdk 21 for MediaPipe 0.10.0 generally — treat 24 as current). Source: https://developers.google.com/edge/mediapipe/solutions/setup_android
- GPU delegate: must be created on the thread that will use it (`Delegate.GPU` on `BaseOptions`), and if the model doesn't support GPU it throws at runtime — code falls back to CPU. Source: https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/android and https://github.com/google-ai-edge/mediapipe-samples (HandLandmarkerHelper.kt `DELEGATE_GPU`/`DELEGATE_CPU`).
- **Recommendation for Galaxy S25 Ultra**: CPU delegate is fine. Hand Landmarker is a small two-stage model (palm detector + landmark model) at typical camera-preview resolutions; GPU texture upload/download overhead tends to dominate below ~480p, often making CPU as fast or faster on modern flagship SoCs. Start CPU-only; only test GPU if profiling shows CPU inference is the bottleneck. (General guidance, not S25-Ultra-specific benchmark — no official per-device numbers found.)

## 3. Android API shape

- `HandLandmarkerOptions` fields: `numHands` (default 1), `minHandDetectionConfidence` (default 0.5), `minHandPresenceConfidence` (default 0.5), `minTrackingConfidence` (default 0.5), `runningMode` (IMAGE/VIDEO/LIVE_STREAM). Source: https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/android
- LIVE_STREAM: `.setResultListener(this::returnLivestreamResult)` and `.setErrorListener(...)`; result callback receives `(HandLandmarkerResult, MPImage)` per the sample's `returnLivestreamResult(result: HandLandmarkerResult, input: MPImage)`. Detection call is `handLandmarker.detectAsync(mpImage, frameTimeMs)` — async, result arrives later via listener. Source: https://github.com/google-ai-edge/mediapipe-samples/blob/main/examples/hand_landmarker/android/app/src/main/java/com/google/mediapipe/examples/handlandmarker/HandLandmarkerHelper.kt
- ImageProxy → MPImage (official sample pattern): copy `imageProxy.planes[0].buffer` into a `Bitmap` (`ARGB_8888` in the sample; RGBA_8888 output from CameraX is directly compatible byte-for-byte with `ARGB_8888` bitmap copy), apply a `Matrix` with `postRotate(imageProxy.imageInfo.rotationDegrees)` and, for front camera, `postScale(-1f, 1f, ...)` to mirror, produce a rotated `Bitmap`, then `BitmapImageBuilder(rotatedBitmap).build()`. Source: same HandLandmarkerHelper.kt file above.
- Rotation: always use `imageProxy.imageInfo.rotationDegrees` (not a hardcoded value) — CameraX supplies this per-frame based on device/display orientation.
- Landmarks (`HandLandmarkerResult.landmarks()`): normalized image coordinates, x/y in `[0.0, 1.0]` relative to the (rotated) input image, z relative depth. Source: https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker
- `worldLandmarks()`: real-world 3D coordinates in **meters**, origin at the hand's geometric center — **use world landmarks for hand-shape geometry** (distances/angles between joints) since they are metric and not distorted by perspective/depth-normalization the way image-space landmarks are. Source: https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker
- `handedness`: classification is computed **assuming the input image is mirrored** (i.e., assumes a selfie/front camera already flipped horizontally); if you feed an unmirrored image, swap the reported handedness in your app. Since the official sample mirrors the bitmap itself before inference for front camera, handedness comes back correct as-is when you mirror per §3 above. Source: https://github.com/google/mediapipe/issues/3407 discussion, corroborated by HandLandmarkerHelper.kt mirroring logic.

## 4. Threading + backpressure

- Official CameraX pattern: `ImageAnalysis` configured with `setBackpressureStrategy(ImageAnalysis.STRATEGY_KEEP_ONLY_LATEST)` so slow inference drops stale frames instead of queuing; each accepted frame is converted and passed to `detectAsync(mpImage, frameTime)` where `frameTime = SystemClock.uptimeMillis()`. Source: https://github.com/google-ai-edge/mediapipe-samples (HandLandmarkerHelper.kt + CameraFragment.kt) and https://developer.android.com/media/camera/camerax/analyze
- Timestamps must be **monotonically increasing** milliseconds (the sample uses `SystemClock.uptimeMillis()`); LIVE_STREAM mode throws/reorders incorrectly if timestamps go backward or repeat.
- GPU delegate requires the landmarker be created and used on the same thread; CPU delegate can be created on main thread and invoked from a background/analyzer thread (per code comment in HandLandmarkerHelper.kt).

## 5. Python side

- `mediapipe` on PyPI: latest is **1.0.1** (Aug 2026); classifiers list Python 3.9–3.12 support but recent PyPI listing shows wheels tagged generically ("py3") rather than per-cp312 tags for some platforms — verify `pip install mediapipe` resolves cleanly under your uv-managed 3.12 venv before relying on a specific cp312 tag. Earlier explicit cp312 wheels appeared starting **0.10.14**, confirmed present by **0.10.18**. Source: https://pypi.org/project/mediapipe/ , https://pypi.org/project/mediapipe/0.10.18/
- IMAGE-mode batch API: `HandLandmarkerOptions(base_options=BaseOptions(model_asset_path=...), running_mode=VisionRunningMode.IMAGE)`, then `landmarker.detect(mp_image)` per image (no timestamp needed in IMAGE mode). Source: https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/python
- Identical landmark semantics vs Android: use the **same `.task` model file** and the **same input orientation convention** (mirror front-camera-style images before feeding Python too, if your training images are meant to represent selfie-camera capture) — landmark index order (21 points, wrist=0) and image/world coordinate definitions are identical across platforms; only mirroring/rotation handling is your app's responsibility, not the model's.

## Recommendation

Pin `com.google.mediapipe:tasks-vision:1.0.0` via Google's Maven repo, minSdk 24, CPU delegate by default. Use the official `hand_landmarker.task` full model, keep Apache-2.0 LICENSE text + a short attribution line alongside the redistributed model file. Mirror-then-rotate ImageProxy→Bitmap→MPImage exactly like the official sample, use `worldLandmarks()` for shape geometry, `STRATEGY_KEEP_ONLY_LATEST` + monotonic `uptimeMillis()` timestamps for LIVE_STREAM backpressure. On the Python side pin a `mediapipe>=0.10.18` release confirmed to have a cp312 wheel, and reuse the same `.task` file for training-pipeline parity.
